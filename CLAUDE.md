# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Internal finance app for the Craze group: receivables and dunning, payables and approvals, cashflow forecasting, risk, inventory valuation, BWA reports, and insurance/contract storage. All data comes from **Microsoft Dynamics 365 Business Central (BC)**. Built with Next.js 16 App Router, React 19, Prisma 5 on PostgreSQL, and Tailwind 4. Deployed on Vercel. The UI text, route names and most comments/log messages are in **Spanish**; keep new user-facing strings in Spanish.

## Commands

```bash
npm run dev        # next dev + src/scripts/cron.ts (BC sync every 5 min) run concurrently
npm run build      # prisma generate && next build
npm run lint       # eslint (eslint-config-next)
npx prisma generate            # after editing prisma/schema.prisma
npx prisma db push             # sync schema to the DB (no migrations folder exists)
npx tsx src/scripts/<name>.ts  # run a one-off script (sync, debug, data fixes)
```

There is no test suite. The files in `src/scripts/` named `test*.ts` / `check*.ts` / `debug*.ts` are ad-hoc scripts that call BC or the DB directly. They are not tests.

Env vars: `DATABASE_URL`, `DIRECT_URL` (Postgres), `JWT_SECRET`, `OPENROUTER_API_KEY` (+ optional `OPENROUTER_MODEL`; AI features), `GEMINI_API_KEY` / `ANTHROPIC_API_KEY` (fallbacks), and the Vercel Blob token for uploads. BC credentials and SMTP settings are **not** env vars. They live in the DB (`BusinessCentralConfig` / `EmailConfig`, single row with `id = 1`) and are edited on `/settings`.

## Architecture

**Data flow: BC is the source of truth, Postgres is a cache with app-only fields on top.**
`src/lib/bcSync.ts` → `syncBusinessCentral(company?, step?)` pulls customers, open customer ledger entries (→ `Invoice`), vendors, open vendor ledger entries (→ `PurchaseInvoice`) and recurring purchase lines for each company. It runs from four places: the `cron.ts` loop in dev; the GitHub Actions workflow `.github/workflows/sync-bc.yml` every hour in production (company × step against the deployed app, `APP_URL` repo variable, default craze-finance.vercel.app); `POST /api/sync-bc` (body `{company, step}`) from the UI buttons through `syncFromBc` (`src/lib/syncClient.ts`, one call per company × step from `src/lib/syncSteps.ts` to stay under Vercel's 60s `maxDuration`; the dashboard's "Actualizar desde BC" uses it too); and scripts such as `runSync.ts`. Each successful step stores `sync:last:<company>` in ApiConfig; `GET /api/sync-bc` returns those times (shown on the dashboard).
- It prefers the **custom BC API** `api/craze/integrations/v1.0` (salesperson, confirmed payment date and similar fields) and falls back to standard `api/v2.0` / `ODataV4` when that API isn't available. Field names differ between these sources, so the mapping code checks several candidates (`c.number || c.no`, and so on).
- Salesperson names come from BC's Salesperson/Purchaser table (`src/lib/salespeople.ts`: custom API entity or OData service matching `/sales.?pe(rson|ople)/i`, or setting `salespeopleService`; cached 6 h).
- Rows are upserted by `@@unique([bcId, companyId])`. Ledger entries that are no longer open in BC get `status: 'Closed'` and are not deleted. Status is computed at sync time (`Open`/`Overdue` from `dueDate`).
- Fields owned by the app (`cashflowDate`, `isArchived`, reminder counts, the approval fields on `PurchaseInvoice`, `noPayment`, `schedulePaymentDate`, and so on) must survive a re-sync. When you change the sync, don't overwrite them.

**Multi-company.** `companyId` is the BC company *name* string (`'CRAZE'`, `'Craze Iberia SL'`, …), not an ID. The UI keeps the selection in `CompanyContext` (`src/contexts/CompanyContext.tsx`), which writes both localStorage and a `craze_selected_company` cookie. API routes read that cookie (`cookies().get('craze_selected_company')`, defaulting to `'CRAZE'`) to scope their queries, so pages generally don't pass the company explicitly. `'ALL'` is a UI-only option. The company lists are hardcoded in `CompanyContext`, `bcSync.ts` and `settings/page.tsx`; keep them in sync. The sync matches on the BC company `name`, not its display name (e.g. `Craze UK` is displayed as "CRAZE Toys Ltd" in BC). Per-company letterhead/bank details live in `src/lib/reportBuilder.ts`.

**Auth.** Custom JWT (`jose`, HS256, 24h) in the `auth-token` cookie, issued by `/api/auth/login` against `User.passwordHash` (bcrypt). `src/middleware.ts` enforces module permissions on **UI routes only**. `User.permissions` is a JSON-string array (e.g. `["dashboard","cashflow","configuracion"]`), and the middleware maps routes to permission names (e.g. `/movimientos` → `movimientos_abiertos`, `/pagos` → `pagos_proveedor`). `/settings` needs `configuracion` or `admin`. API routes are not permission-checked. The middleware passes `x-user-*` headers through, and `getSession()` in `src/lib/auth.ts` reads the cookie server-side. When you add a new module page, add it to `protectedUiRoutes`/`permissionMap` and to the module list in `src/components/Sidebar.tsx`. Each user can group the sidebar items into their own collapsible sections ("Organizar menú": create/rename/delete sections, drag items between them); the layout is stored per user in `ApiConfig` `sidebar:layout:<username>` via `/api/sidebar-layout`, and items in no section stay at the top in the default order.

**Audit log.** Call `logAction(action, details?)` from `src/lib/logger.ts` in mutating API routes. It records the session user and the selected company in `ActionLog`, which is shown at `/settings/logs`.

**Page width.** Pages use the full width of the main area with small side padding (`w-full px-4 md:px-8`, or `p-8` on simple pages, like BWA Analytics). Don't wrap page content in `max-w-* mx-auto` containers; wide tables must not be cut off. Narrow widths are only for modals, forms (`/settings`) and text cells.

**Pages are large client components.** Each module is a single `'use client'` `page.tsx` (cashflow is about 1.2k lines) that fetches from `/api/*` and holds its state locally. There is no shared data layer or component library beyond `Sidebar` and `CustomerCard`.

**Other integrations.**
- Dunning (`/recobros`): `reportBuilder.ts` builds the statement HTML, `/api/preview-report` renders it, the client turns it into a PDF with `html2pdf.js`, and `/api/send-email` / `/api/send-salesperson-email` send it with nodemailer using the SMTP config from the DB (falls back to Ethereal when none is set). Sent reminders are recorded in `Reminder`.
- Insurances and contracts: files are uploaded to Vercel Blob through `/api/upload` (a public route). `*/extract` routes pull out the dates and parties and `*/bot` routes answer questions about the stored documents, through `generateText` in `src/lib/ai.ts`: OpenRouter (`OPENROUTER_API_KEY`, model `OPENROUTER_MODEL`, default `anthropic/claude-sonnet-5.5`, PDFs sent as `file` parts) or, without that key, Gemini (`GEMINI_API_KEY`, `gemini-flash-latest`).
- Cashflow merges open invoices and purchase invoices (by `cashflowDate`/`confirmedPaymentDate`/`dueDate`), active `RecurringPayment`s, `CashflowManualEntry` rows, and per-company/currency starting balances (`CashflowConfig`). The default account/consolidated currency is CHF for CRAZE Group AG and EUR elsewhere. "Min. Saldo Consolidado" (next to the consolidated balance) is stored per company in ApiConfig `cashflow:minBalance:<company>` (`{amount, currency}`, via `/api/cashflow/min-balance`); a banner warns when the consolidated balance is below it or the projected balance of the open account first drops below it (converted with the day's rates), and those rows are flagged "Bajo mínimo".
- Payment-method codes such as `MARKANT` (factoring) change how invoices are handled in cashflow and dunning. Check recent commits before touching that logic.

**Dashboard (`/`, `GET /api/dashboard`).** Built from the synced Postgres data, except the "Pagos Internacionales (China)" cards, which come live from BC through `payablesReport` (same as Reporting: open vendor entries whose own payment method is CHINA TRF, remaining amount in LCY, confirmed = Scheduled Payment Date set; cached 1 h, stale-while-revalidate), falling back to the synced data if BC fails.

**Reporting (`/reporting`).** Monthly management report (Operacional / Dirección tabs, month selector, ES/EN/DE, PDF via the browser print dialog with the print CSS in `globals.css`). It replicates a report built from BC exports and two Power BI files, but reads BC live:
- One route per block, `/api/reporting/<section>?month=YYYY-MM[&force=1]`, backed by `src/lib/reporting/*`. Heavy BC reads are cached in `ApiConfig` (`reporting:cache:*`, see `cache.ts`); `REPORTING_NO_CACHE=1` bypasses the DB for scripts. `cached()` is stale-while-revalidate (used by Reporting, Controlling and Royalties): it always returns the last stored data at once and, when it is older than 1 h (or its shorter max age), recomputes it in the background with `after()` (lock key `reporting:refreshing:*` so only one refresh runs). It only waits for BC when nothing is stored or with `force=1` (the refresh button). Caches longer than a day (AI key points by content hash) aren't refreshed hourly.
- Inventory (`inventory.ts`): OData `ValueEntries` (a BC Query: no `$orderby`/`$apply`, fetched in parallel by `Entry_No` ranges), excluding entries without `Item_No`; matches page 80016 "Inventory Value CRZ". Value per location = location qty × item unit cost. The 2023 depreciation % per item is a fixed list (setting `depreciation2023`).
- Receivables/payables (`ledgers.ts`): custom API `custLedgerEntries` / `vendorLedgerEntries`. "Open at month end" = posted ≤ date and (open, or closed after the date); BC rejects `or` across fields, so it runs two queries. INTERGROUP is excluded from customer receivables; CHINA TRF confirmed = `scheduledPaymentDateBCT`.
- Provisions (`provisions.ts`): `General_Ledger_Entries_Excel`, every entry with `Document_No` starting with `PROV` (PROV-00049… and also PROV1, PROV3… royalty reinvoicing) posted in the report year up to the cutoff. Each month a new PROV document re-estimates a provision against a balance-sheet account (3071 13 Konditionen, 3071 12 Lizenzen, 3071 08 KAM, 3072 01 Marketing, 3072 02 Amazon Promotions). A document's series is the provision account (30xx) of its first entry on one; PROV documents without a 30xx account (PROV1, PROV3: royalty reinvoicing against 3401 01 / 1260 01) are not provisions made and are left out here (they count as consumed royalties in Controlling). The open amount of a series is that account's balance over all its PROV entries, shown on the series' latest document. That row's original is the year's provisions in the series: what its documents post to income-statement accounts (classes 4–7: 4769 02, 6020 10, 6600 30, 6600 31, 6837 00), matching the P&L balances and consumed = original − open. Series 3072 02 is its own type, Amazon Promotion. Amounts are shown with the expense sign (e.g. PROV-00049 CRAZE 09/2026: open 472.987,87 = 3071 13). `/api/reporting/provision-check?doc=&month=&company=` shows the live calculation for one document.
- BWA (`bwa.ts`): custom `glEntriesUnion` + `mappingAccounts` + `bwas` (Formula lines sum other codes), GBP/CHF converted with `Currencies_Excel`, sign inverted. A company column includes its elimination entries; Intercompany = elimination entries; Consolidated = everything else.
- Cashflow (`cashflowReport.ts`) reuses `src/lib/cashflow.ts`, overdraft limit setting `overdraftLimit` (default −1 M€), 4-month horizon. Key points are generated by AI (`summary.ts`) from the figures the page already loaded: OpenRouter via `src/lib/ai.ts` when `OPENROUTER_API_KEY` is set, else Claude (`@anthropic-ai/sdk`, `claude-opus-5-5`) with `ANTHROPIC_API_KEY`, else Gemini.

**Royalties (`/royalties`).** `GET /api/royalties?from=&to=[&force=1]` → `src/lib/royalties.ts`, cached like reporting. It reads BC page/table 60000 "AIT Documents LM Components" through its OData web service. The service is found by name (`/lm_?components?|royalt/i`) unless setting `royaltiesService` sets it, and field names are matched against candidate lists. The User Setup record for the app user ACOUNTING must exist in each company or BC refuses the page. If BC fails, the page shows the error; there is no Excel fallback. Lines with Main Item are dropped, and so are intercompany lines (`isIntercompany`: INTERGROUP customer, customer named "CRAZE …", customer dimension "Craze Intercompany", or VAT group INTERCOMPANY…). The LM Royalty Code is ignored. The code always comes from the item card (table 27) in company `CRAZE` (GmbH): the custom API `items`, or an OData page whose name starts with Item and has a `royalt*` field (setting `royaltiesItemService`), cached 6 h. An item with no card there takes its base item's code (letters stripped off the end, e.g. 48412MEILI → 48412), or else keeps its LM code. The LM provision is ignored too. Provision = turnover × % Domestic Royalty (% FOB Royalty when the shipment method is FOB, unless the code's % FOB is 0) from page 80007 "Royalties" in `CRAZE`, OData service `RoyaltiesCRZ` (setting `royaltiesRatesService`), cached 6 h. Contract dates are not applied, the same as in BC's LM. The code field is `License_No`. If RoyaltiesCRZ can't be read, the report keeps the LM's own provision (`Total_Provision_Royalties`) and shows a warning. UK amounts are in GBP and Group AG amounts in CHF (`companyCurrency`). The page can show them in EUR using the `Currencies_Excel` rate of CRAZE (the same one the BWA uses). The rate is editable and the conversion is done client-side. A code missing from that table has no provision and is listed on the page. Licences a company may not sell are left out (`EXCLUDED_CODES`: BLUEY in UK). The rest is grouped by Royalty Code × bill-to country × item. Price = turnover ÷ qty and rate = provision ÷ turnover. The default period is the last calendar quarter. In CRAZE the page also shows a group summary (`GET /api/royalties/group`, `groupRoyaltiesReport`). It has one row per licence and one column per company in `GROUP_COMPANIES`, each from BC, converted to EUR on the page with the editable `Currencies_Excel` rates. Below it is the Minimum Guarantee summary (`GET /api/royalties/mg?to=`). The contracts and instalments live in `src/lib/royaltyContracts.ts`, and several Royalty Codes can feed one licence (Toys + Cosmetic). For each guarantee, the group's provision from the contract start up to `to` is assigned by billing country (Viacom: GSA vs UK/Channel Islands; Bluey: everything except UK). Each contract has an `owner` company and contracts are sorted by owner in `GROUP_COMPANIES` order. The MG route returns the provision by code, country and date (`buildReport(..., trackDates)`). Each instalment active at `to` opens a period that runs until the next instalment or `to`; the first period starts at the contract start. That period's Provision Royalty goes to MG while active MG remains, including MG left over from earlier instalments, and the rest is Royalty to Invoice. To MG + To Invoice = Provision on every row. Future instalments are shown but not consumed.

**Controlling (`/controlling`).** Several controlling reports switched with header tabs, like Reporting. Each report (except Consumed Provisions, which uses the menu company) has its own CRAZE Company selector (`CompanySelect.tsx`, starts from the menu company, passes `?company=` to the API) with a "CRAZE Consolidated" option that loads every company and merges them in the browser: Order Intake and Ventas por licencia in EUR (`eurRate` from CRAZE `Currencies_Excel`), Compras por artículo/proveedor merged by item with each vendor tagged with its company (`purchaseData.ts`); BWA año a año is per company only. Any view that drills down to purchase invoices offers an "Agrupar por" selector (month, vendor, Source Code/account, none) and sortable columns.
- Compras por artículo: `GET /api/controlling/purchase-items?from=&to=` → `src/lib/controlling/purchaseItems.ts` (cached 1–6 h). Posted purchase invoice lines (custom API `purchInvLines`, type Item) + headers (`Posted_Purchase_Invoice_Excel`), credit memos from an OData service for page 140 with its lines (found by name `/purch.*cr.?memo/i`, not the `CS_` Document Capture ones) or, while it isn't published, from G/L Entries (purchase entries of each credit memo grouped by Gen. Prod. Posting Group → the item with that group, no quantity/unit cost; header dates from `CS_PostedPurchaseCrMemos`), item card (v2 `items`; the `Item_Card_Excel` page takes >30 s), vendor card (`Vendor_Card_Excel`), General Posting Setup (`General_Posting_Setup_Excel`, current Purch./Cr. Memo account per bus. × prod. group) and the historical G/L account from `General_Ledger_Entries_Excel` (Gen. Posting Type Purchase, same document and Gen. Prod. Posting Group as the line). Items of type Inventory are excluded. Item → vendor → documents; item/vendor pairs with as many credit memos as invoices, or whose net is 0, are dropped.
- Compras por proveedor (`PurchaseVendorsView.tsx`): the same `/api/controlling/purchase-items` data regrouped vendor → item → documents (grouping by month, G/L account or invoice/credit memo), to check each vendor invoices the right items.
- BWA año a año: two uploaded P&L Excel files (`src/lib/controlling/plParse.ts`, parsed in the browser: DATEV BWA or the group BWA export, sign normalised to income +/costs −), stored per company in `ApiConfig` `controlling:pl:<company>:<A|B>` via `/api/controlling/pl`. Rows are paired by label or a DATEV↔group synonym list (editable per row, kept in localStorage); % on a selectable reference row; selected months only; top cost increases/decreases.
- Consumed Provisions: `GET /api/controlling/consumed-provisions?from=&to=` → `src/lib/controlling/consumedProvisions.ts`. Provisioned = PROV* entries in the period on the income-statement provision accounts (4769 02 Conditions, 6020 10 KAM, 6600 30 Marketing, 6600 31 Amazon Promotion, 6837 00 Royalties), i.e. the P&L balances. Shown next to it for reference, the LM calculation (page 60000 without Main Item lines): Conditions = `Total_Provision_Sales`, KAM = "Provision HHRR" (`Total_Provision_Bonus`), Royalties = `Total_Provision_Royalties`, Marketing = `Provision_Marketing` without Amazon customers, Amazon Promotion = `Provision_Marketing` on Amazon lines. Consumed = everything a purchase invoice/credit memo has on PROV-KONDITIONS / PROV-KAM / PROV-MARKETING / PROV-ROYALTIES / PROV-AMZPROM in the period, following the Document No. (purchase posting, PUR-DEFER releases and journal reclassifications posted with the same document number); PROV + number documents (PROV1, PROV3: royalty reinvoicing), journal documents on those accounts with no purchase document behind them (Skonto Reclassification…) and, in PROV-… documents, whatever reduces the concept's provision account (3071 13, 3072 01, 3072 02, 3071 12) against other balance accounts (= series account + P&L + PROV-* account, e.g. PROV-00049's transfer from 3071 06) also count, so consumed matches the Reporting (provisioned − open). The page also shows the LM calculation by `Customer_Group_Code` (name from the custom API `customerGroups`) next to what that group consumed: purchase invoices/credit memos whose vendor is one of the group's LM customers, matched by VAT number, then exact normalised name, then first word when it fits only one group, then the Customer Group name (all its words except the country must be in the vendor name; a matching country wins). In that table Conditions excludes Markant: the LM's `Provision_Accounting_Partner` is its own column, and Markant's invoices (vendor `/markant/i`, no group on them) are spread across groups in proportion to that calculated Markant. `VENDOR_OVERRIDES` forces a vendor to a group (and optionally a concept) there: Savi Marketing → dm DE 017 (concept from its account, Marketing); dm DE, Rossmann, REWE Zentral, EDEKA Zentral, Amazon EU.
- Ventas por licencia: `GET /api/controlling/license-sales?from=&to=` reuses `royaltiesReport` (same LM lines, item-card Royalty Code, no Main Item/intercompany) and returns Turnover Net of Provision Sales, Amount (LM field `Amount`, optional) and qty by code; a dropdown on the page picks Amount, Turnover, Provision Royalties (same calculation as Royalties) or units. Each code expands to a sub-level chosen on the page: ship-to country (LM `Ship_to_Country_Region_Code`, bill-to country if not published) or Customer Group (`Customer_Group_Code`, names from custom API `customerGroups`); `buildReport` returns this as `breakdown`. The page (`LicenseSalesView.tsx`) asks one period per year (1 Jan → the same day, default end = last day of previous month) for the active company and compares them (Δ vs previous year, Excel export).
- Facturación según Order Date: `GET /api/controlling/order-intake?year=&from=M&to=M[&open=1]` → `src/lib/controlling/orderIntake.ts`, one call per year (selected year + 2 previous), always January–December. Invoices are read by quarter in parallel; the current year is refreshed hourly like the rest, closed years every 12 h. Billed = customer ledger entries of type Invoice minus Credit Memo (custom `custLedgerEntries`, `salesLCY` = amount excl. VAT in LCY) by posting month, only when the document exists in v2 `salesInvoices` / `salesCreditMemos` (entries whose Document No. ends in `*` are migration duplicates with no document behind them and are left out); intercompany customers (payment method INTERGROUP or name starting with "CRAZE") are excluded from invoices and open orders; the invoice's order number comes from v2 `salesInvoices.orderNumber`, and its Order Date from the open order (custom `salesHeaders`, type Order) or the archived order (v2 `salesOrderArchives`; posted invoices don't publish Order Date). Per month: billed by posting date (expandable by order age: same month, 1, 2, 3+ months earlier, no order, order not found, credit memos) and "Order Date del mes" = Order Intake: every sales order created that month = what is already invoiced of it (invoices of all loaded years, any posting month) + what is still open today (open orders are requested with the selected year and used for all years), split into "Abierto RDD mes" (Requested Delivery Date within the order month), "Abierto RDD mismo año" and "Abierto RDD próx. año"; plus "Abierto RDD mes (meses anteriores)" = open orders created in earlier months whose RDD is in that month (not part of the intake). Open amount per order = order amount excl. VAT (custom `salesHeaders.amount` / currencyFactor) − everything already invoiced of that order across the loaded years (recomputed in the browser). The open columns are shown only for the selected year; the % is the intake growth vs the same month of the previous year. Column widths are adjustable by dragging the header edge (`ResizableColumns.tsx`: `useColumnWidths` + `ResizeTh`, saved in localStorage; headers wrap to their width), reusable in other tables.
- BWA (Power BI): recreates the Power BI "BWA" (pages Annual, Monthly, Annual - Detail, Exchg_Cur). `GET /api/controlling/bwa-pbi?year=` → `src/lib/controlling/bwaPbi.ts` (always read from CRAZE, all companies; cached 1 h / 12 h for closed years) returns the BWA lines, mapping accounts (shown by G/L account No., ordered by BWA level) and `glEntriesUnion` aggregated by company × elimination × account × month for the year and the previous one, sign inverted, GBP/CHF × `Currencies_Excel`. `BwaPbiView.tsx` builds the pages: Annual = YTD to the chosen month vs previous year with % on SALES REVENUES and the change in points (red when it drops), plus a "Principales desviaciones" block (the 6 BWA lines with the largest € change and their top 4 accounts; clicking an account opens its drill-down; Annual - Detail shows the same block for the consolidated figures with the change per company and Intercompany); Monthly = each month; Detail = one column per company + Consolidated. Column rules as in the DAX: a company = all its entries, Intercompany = elimination entries, Consolidated = the rest. The Budget column of the Power BI comes from its remote dataset and is not reproduced. "Annual vs DATEV" (`datev` page) is Annual with Year -1 taken from an uploaded DATEV Jahresübersicht (`datevParse.ts`; stored per company/year in ApiConfig `controlling:bwa-datev:<company>:<year>` via `/api/controlling/bwa-pbi/datev`): DATEV account 602000 = BC 6020 00 with the BC mapping (`DATEV_ACCOUNT_OVERRIDES` first adds some DATEV accounts to a chosen BC account, e.g. 6010–6030 → 6000 00, 6113/6140 → 6110 00, 6640 → 6650 00, 6770 10 → 6770 00, 6800 12 → 6800 00); unmapped accounts go to the line of a mapped account with the same first 4 digits, else by DATEV section (`DATEV_SECTION_LINE`) and are listed as extra "DATEV" rows; income sections (1020, 1040, 1090, 132x) keep their sign, the rest is negated. Extra columns Year -1 BC and DATEV − BC. Each account row drills down (`BwaAccountDrill.tsx`): clicking the account opens the page's main column (Annual: Year, Monthly: Total, Detail: Consolidated), clicking an amount opens exactly that company/period (e.g. one month). `GET /api/controlling/bwa-pbi/detail?account=&scope=&from=&to=` (`bwaPbiDetail.ts`) takes that mapping account's `glEntriesUnion` entries and joins each company's `General_Ledger_Entries_Excel` by Entry No. (document type/no., Source Code/Type/No., description, bal. account) plus v2 vendor/customer names; the page groups entries into documents by company + Document No. + posting month (a journal posted in several months appears in each month) and splits them into purchase documents / sales documents / journals, groups by month, vendor/customer or Source Code, then documents → G/L entries and the document lines with the item (`/api/controlling/bwa-pbi/lines`, custom `purchInvLines` / `purchCrMemoLines` / `salesInvoiceLines` / `salesCrMemoLines`, loaded on expand).
- Cancelled invoices: `src/lib/controlling/cancelledDocs.ts` (`vendorCancelPairs`) pairs each purchase credit memo of the period with the invoice it cancels in full (same vendor, opposite amount), linked through the custom `vendorLedgerEntries` application fields (applies-to doc, `correctedInvoiceNoBCT`, Closed by Entry No. either way). BWA drill-down, Compras por artículo and Consumed Provisions hide a pair when both documents are in their data and sum 0 (`hiddenByPairs`), so only the correct invoice is listed and totals don't change.
- `GET /api/controlling/bc-services?match=` lists the BC OData services / API entities and their fields (diagnostic).

**Intercompany (`/intercompany`, own menu entry; view `src/app/controlling/IntercompanyView.tsx`).** `GET /api/controlling/intercompany?company=&from=&to=` → `src/lib/controlling/intercompany.ts` (cached 1 h / 12 h), one call per issuing company (consolidated = all). Posted sales invoices (v2 `salesInvoices`) to group companies (customer name starting with CRAZE, mapped by `IC_COMPANIES`) are matched with the purchase invoice in the other company (v2 `purchaseInvoices` from that vendor, Vendor Invoice No. = sales invoice no.; a trailing dot is accepted, other spacing differences are flagged) and compared on amount excl. VAT, currency (blank = company LCY: CRAZE/Iberia/Entertainment EUR, UK GBP, Group AG CHF), invoice date and item quantities (custom `salesInvoiceLines` / `purchInvLines`; accepted equivalence: in Craze Entertainment purchases the GmbH foilbag items are booked as AA-00049). Drop shipment CRAZE → UK / Group AG: the final sales invoice in that company is found by number or External Document No. = the GmbH invoice's External Document No., and its items/quantities are compared. Purchases from a group company with no matching sales invoice in the period are listed separately. Zero-amount invoices that were credited (v2 `salesCreditMemos` with that invoice number or the same External Document No. and company) are left out with their credit memo and listed. Credit memos are not compared yet.

**Commercial Analysis (`/commercial`).** Recreates the Power BI "Commercial Analysis" (pages YoY Status, Sales Performance, Budget Summary/Analysis/MoTD vs. Forecast, Rule 80-20, Top 50 Items) live from BC. `src/lib/commercial/commercial.ts`: `commercialDims` (CRAZE: custom `items` — the Item_Card_Excel page is too slow —, `customerGroups`, `salesperonCustomerGroups`, OData `AIT_14_Salespeople`, `Dimension_Values_Excel`; cached 6 h) and `commercialFacts(company, year)` per Power BI company (GmbH = CRAZE, UK = Craze UK, Swiss = CRAZE Group AG, Asia = CRAZE Macau LTD): invoiced = custom `documentsLMComponents` (lineAmountEUR, local amount as the Power BI: GmbH lineAmountEUR, Swiss lineAmountLCY, others lineAmount), open orders = OData `Sales_Lines_Excel` exactly as the Power BI's `Sales_Lines_Excel_<company>` queries (every line that is not Invoice and has a customer, full Line_Amount and Quantity with no sign, dated by `AIT_Requested_Delivery_Date`, Return Orders by the return's Posting_Date from `Sales_Return_Order_Excel`; any year; CRAZE lines with location ASIA belong to Asia; customer group/country from CRAZE's `Customer_Card_Excel`; EUR = 1 / CRAZE `Currency_Exchange_Rates` at the line date), budget/forecast = custom `budgetItems`/`budgetUnits` and `forecastItems`/`forecastUnits`; Customer Group 223 and items without product line or in BU PUBLISHING are excluded; KAM = `salesperonCustomerGroups` by Customer Group × item BU, else the group's salesperson. Rows are aggregated by month × part of month (≤ today's day) × class (normal / Main Item / component) × Customer Group × KAM × sell country × ship country × item (`/api/commercial/facts?company=&year=`; stored and refreshed in the background every 6 h for the current year and daily for closed years, master data daily; `cached(..., { refreshAfterMs })`). `src/app/commercial/engine.ts` computes the DAX measures in the browser: Sell-in = invoiced + open orders, previous year = same period, amounts in local currency for one company and EUR for several, units × Item To Root units when chosen, projection = invoiced for closed months and forecast for the rest. The Sell-out page is not recreated yet (sources: OData `SellOuts_CRZ` by GTIN and `SellIn_B2C`).

**Payment Proposal (`/payment-proposal`).** `GET /api/payment-proposal?from=&to=` → `src/lib/paymentProposal.ts`, live (no cache). It reads custom API `vendorLedgerEntries` for the selected company with fixed filters: open, document type Invoice or Credit Memo (`VENDOR_INVOICE_TYPES`), `paymentMethodCode eq 'TRANSFER'`, due date in range, No Payment = No (`noPaymentBCT` / onHold `NO PAGAR`), and vendors not starting with "CRAZE". It replicates two pivots from the user's BC export. "Approved for Payment" is `% Payment Approval` (`paymentApprovalCRZ`) ≥ 100, by vendor. "Pending Approval" is < 100, grouped by Pending Users and then vendor. Pending/Approval Users come from the custom API (it now returns pending users). If the API has no pending field, they are read from the vendor ledger page published in OData (`/vendor.?ledger.?entr/i`, `*_Excel` first, or setting `paymentProposalUsersService`) and joined by Entry No. Failing that, pending = approval users − approved users − rejected users. If nothing is available, the page shows a warning and the API field list. Amounts are Remaining Amount per document currency, plus a total in LCY. Vendor rows expand to their documents.

**Notas de compra (`/notas-compra`).** The BC "Notes" FactBox of purchase invoices/credit memos = Record Links of type Note (table 2000000068, text in a BLOB), not available in v2/OData. `src/lib/purchaseNotes.ts` reads them from the custom API entity `recordLinks` (setting `purchaseNotesEntity`; expected fields linkId, tableNo, recordIdText, documentNo, vendorNo, vendorName, created, userId, toUserId, type, company, noteText), keeps tables 38 (Invoice/Credit Memo), 122 and 124, cached 10 min. Read state is app-only, in ApiConfig `notes:read:<company>` (`{linkId: {by, at}}`), set through `PATCH /api/purchase-notes` (one or several at once, logged). The dashboard shows the unread count ("Notas sin leer"). Until BC publishes `recordLinks` the page shows a warning and the KPI shows "—".

**D-FORCE (`/dforce`, only for Craze Entertainment).** It turns the monthly D-FORCE-ONE Gutschrift (PDF) and its Curasoft Excel export into lines for three BC documents. `POST /api/dforce/process` (multipart `pdf`, `excel`) → `src/lib/dforce.ts`. The PDF is read server-side with `unpdf` (rows rebuilt by y position) and the Excel with `xlsx`.
- The document comes from the Excel movement type, never from the PDF appendix. Lieferungen/Lieferdifferenzen (Vorgang 10/11/20/21) go to the Sales Invoice, Remissionen (160/161) to the Credit Memo, and everything else to the Purchase Invoice. Each Excel sales row gives exactly one line. The PDF only supplies the channel (Sparte) and the order, matched by title, issue, quantity and amount. Repeated PDF rows are dropped, and PDF-only or Excel-only rows are reported as warnings.
- Sales Invoice: one line per Lieferungen/Lieferdifferenzen row, with Description 2 = Sparte (channel).
- Sales Credit Memo: RI/RA with positive quantities. Bahnhofsbuchhandel and all RA lines get Return Reason `NON-REC`. BC generates their negative reversal lines itself, so the app doesn't output them. Project Task No.2 is `004.001` on returns without a reason code and empty on NON-REC lines.
- Purchase Invoice: vendor `VE-00111`, from Excel Vorgang 220/230/240/250 grouped by title and issue, mapped to service items AA-00005/06/10 with project tasks 002.00x.
- Item and project come from the TitelNr (`TITLES`: 4191 → 05995/35420, 4192 → 05993/38791, 4193 → 05994 …_SPECIAL) plus the issue suffix `_YYMM`.
- Item description and unit cost are read from BC standard API `items` of Craze Entertainment.
- Check: invoice − returns − purchase = the PDF's "Summe Netto".
- Return provisions (`src/lib/dforceProvisions.ts`, computed client-side so unit costs can be edited), all against 3071 00 as in August 2026:
  - Invoice: `PROV.<GAL|INKE|GALSP><MM>/<YY>` on 4300 00 = 80% of sales, and `INV.PROV.…` on 5881 00 = −(80% of units × unit cost), with a negative journal amount. Only issues delivered that month (LI/LA lines) are provisioned.
  - Credit memo: the returns release both entries at 100%: negative on 4300 00 and positive on 5881 00.
- The page exports the "Output Format" config-package layout: sheets `Sales Line` (37) and `39 Purchase Line` with the document numbers typed on the page, plus a `Provisiones 3071 00` journal sheet.

Path alias: `@/*` → `src/*`. `src/lib/prisma.ts` exports the singleton client. Use it instead of `new PrismaClient()`, except in standalone scripts.
