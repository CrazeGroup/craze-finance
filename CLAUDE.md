# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Internal finance app for the Craze group: receivables and dunning, payables and approvals, cashflow forecasting, risk, inventory valuation, BWA reports, and insurance/contract storage. All data comes from **Microsoft Dynamics 365 Business Central (BC)**. Built with Next.js 16 App Router, React 19, Prisma 5 on PostgreSQL, and Tailwind 4. Deployed on Vercel. The UI text, route names and most comments/log messages are in **Spanish**; keep new user-facing strings in Spanish.

## Commands

```bash
npm run dev        # next dev + src/scripts/cron.ts (BC sync every 5 min) run concurrently
npm run build      # prisma generate && next build
npm run lint       # eslint (eslint-config-next)
npx prisma generate            # after editing prisma/schema.prisma
npx prisma db push             # sync schema to the DB (no migrations folder exists)
npx tsx src/scripts/<name>.ts  # run a one-off script (sync, debug, data fixes)
```

There is no test suite. The files in `src/scripts/` named `test*.ts` / `check*.ts` / `debug*.ts` are ad-hoc scripts that call BC or the DB directly. They are not tests.

Env vars: `DATABASE_URL`, `DIRECT_URL` (Postgres), `JWT_SECRET`, `OPENROUTER_API_KEY` (+ optional `OPENROUTER_MODEL`; AI features), `GEMINI_API_KEY` / `ANTHROPIC_API_KEY` (fallbacks), and the Vercel Blob token for uploads. Amazon Vendor SP-API: `SP_API_CLIENT_ID`, `SP_API_CLIENT_SECRET`, `SP_API_VENDOR_REFRESH_TOKEN_<DE|FR|…>`, `SP_API_MARKETPLACE` (default DE). BC credentials and SMTP settings are **not** env vars. They live in the DB (`BusinessCentralConfig` / `EmailConfig`, single row with `id = 1`) and are edited on `/settings`.

## Architecture

**Data flow: BC is the source of truth, Postgres is a cache with app-only fields on top.**
`src/lib/bcSync.ts` → `syncBusinessCentral(company?, step?)` pulls customers, open customer ledger entries (→ `Invoice`), vendors, open vendor ledger entries (→ `PurchaseInvoice`) and recurring purchase lines for each company. It runs from four places: the `cron.ts` loop in dev; the GitHub Actions workflow `.github/workflows/sync-bc.yml` every hour in production (company × step against the deployed app, `APP_URL` repo variable, default craze-finance-iota.vercel.app (the old craze-finance.vercel.app is another deployment without the current env vars)); `POST /api/sync-bc` (body `{company, step}`) from the UI buttons through `syncFromBc` (`src/lib/syncClient.ts`, one call per company × step from `src/lib/syncSteps.ts` to stay under Vercel's 60s `maxDuration`; the dashboard's "Actualizar desde BC" uses it too); and scripts such as `runSync.ts`. Each successful step stores `sync:last:<company>` in ApiConfig; `GET /api/sync-bc` returns those times (shown on the dashboard).
- It prefers the **custom BC API** `api/craze/integrations/v1.0` (salesperson, confirmed payment date and similar fields) and falls back to standard `api/v2.0` / `ODataV4` when that API isn't available. Field names differ between these sources, so the mapping code checks several candidates (`c.number || c.no`, and so on).
- Salesperson names come from BC's Salesperson/Purchaser table (`src/lib/salespeople.ts`: custom API entity or OData service matching `/sales.?pe(rson|ople)/i`, or setting `salespeopleService`; cached 6 h).
- Rows are upserted by `@@unique([bcId, companyId])`. Ledger entries that are no longer open in BC get `status: 'Closed'` and are not deleted. Status is computed at sync time (`Open`/`Overdue` from `dueDate`).
- Fields owned by the app (`cashflowDate`, `isArchived`, reminder counts, the approval fields on `PurchaseInvoice`, `noPayment`, `schedulePaymentDate`, and so on) must survive a re-sync. When you change the sync, don't overwrite them.

**Multi-company.** `companyId` is the BC company *name* string (`'CRAZE'`, `'Craze Iberia SL'`, …), not an ID. The UI keeps the selection in `CompanyContext` (`src/contexts/CompanyContext.tsx`) **per browser tab**, so several tabs can work on different companies at once: sessionStorage (this tab) + localStorage (default for new tabs) + the `craze_selected_company` cookie, rewritten with the tab's company whenever a tab becomes visible/focused (for links and downloads that don't go through fetch). The provider wraps `window.fetch` so every same-origin `/api/` call carries header `x-craze-company` (URI-encoded); `src/middleware.ts` (`withTabCompany`) sets it as that request's `craze_selected_company` cookie. API routes read that cookie (`cookies().get('craze_selected_company')`, defaulting to `'CRAZE'`) to scope their queries, so pages generally don't pass the company explicitly; outside React use `tabCompany()`, never `document.cookie`. `'ALL'` is a UI-only option. Show company names with `companyLabel()` (CompanyContext): CRAZE in capitals and `CRAZE` displayed as "CRAZE GmbH"; the internal identifiers don't change. The company lists are hardcoded in `CompanyContext`, `bcSync.ts` and `settings/page.tsx`; keep them in sync. The sync matches on the BC company `name`, not its display name (e.g. `Craze UK` is displayed as "CRAZE Toys Ltd" in BC). Per-company letterhead/bank details live in `src/lib/reportBuilder.ts`.

**Auth.** Off unless `AUTH_ENABLED=true` (then the whole app and API are public). Custom JWT (`jose`, HS256, 24h) in the `auth-token` cookie (`setSessionCookie`), issued by `/api/auth/login` against `User.passwordHash` (bcrypt) or by Microsoft sign-in (Entra ID OIDC, env `AZURE_AD_TENANT_ID` / `AZURE_AD_CLIENT_ID` / `AZURE_AD_CLIENT_SECRET`, redirect URI `<origin>/api/auth/microsoft/callback`): `/api/auth/microsoft` redirects with state/nonce in a cookie, the callback verifies the id_token against the tenant's JWKS and opens a session for the `User` whose username is the Microsoft email (case-insensitive); unknown emails are refused. The password is optional: a user created without one (empty `passwordHash`, "Microsoft" badge on `/settings/users`, or "Quitar la contraseña" when editing) can only sign in with Microsoft; the password login refuses it. The `admin` permission is the first option in the users editor. With auth on, `/api/*` needs the session cookie or `Authorization: Bearer <INTERNAL_API_TOKEN>` (GitHub sync workflow, diagnostic scripts) and answers 401 otherwise. `src/middleware.ts` enforces module permissions on **UI routes only**; `admin` passes every module check. `User.permissions` is a JSON-string array (e.g. `["dashboard","cashflow","configuracion"]`), and the middleware maps routes to permission names (e.g. `/movimientos` → `movimientos_abiertos`, `/pagos` → `pagos_proveedor`). `/settings` needs `configuracion` or `admin`. API routes are not permission-checked. The middleware passes `x-user-*` headers through, and `getSession()` in `src/lib/auth.ts` reads the cookie server-side. When you add a new module page, add it to `protectedUiRoutes`/`permissionMap` and to the module list in `src/components/Sidebar.tsx`. The sidebar items can be grouped into collapsible sections ("Organizar menú": create/rename/delete sections, drag items between them, drag a section by its title to reorder the sections); the layout is global, the same for every user, stored in `ApiConfig` `sidebar:layout` via `/api/sidebar-layout` (until it exists, GET falls back to the most recently updated old per-user `sidebar:layout:<username>`), and items in no section stay at the top in the default order. Which sections are collapsed is per browser (localStorage `crz-menu-collapsed`). The sidebar is titled "Menu" and can be hidden (it shrinks to a narrow strip on the left, in the layout flow so it never covers the page, with a button and a vertical "Menu" label that bring it back; localStorage `crz-menu-hidden`). Long tables use the `.table-scroll` class (globals.css): the table scrolls inside its card (max height = window minus `--table-offset`, the page header) with the header row sticky; used in Movimientos abiertos and Tracking Cierre Mensual. The app language (`LanguageContext`, EN by default, ES/DE; localStorage `crz-app-lang`) is chosen in the sidebar inside the section whose name starts with "Conf" (or at the bottom if there is none); the menu labels and Reporting follow it, the other pages are still in Spanish.

**Audit log.** Call `logAction(action, details?)` from `src/lib/logger.ts` in mutating API routes. It records the session user and the selected company in `ActionLog`, which is shown at `/settings/logs`.

**Page width.** Pages use the full width of the main area with small side padding (`w-full px-4 md:px-8`, or `p-8` on simple pages, like BWA Analytics). Don't wrap page content in `max-w-* mx-auto` containers; wide tables must not be cut off. Narrow widths are only for modals, forms (`/settings`) and text cells.

**Pages are large client components.** Each module is a single `'use client'` `page.tsx` (cashflow is about 1.2k lines) that fetches from `/api/*` and holds its state locally. There is no shared data layer or component library beyond `Sidebar` and `CustomerCard`.

**Other integrations.**
- Dunning (`/recobros`): `reportBuilder.ts` builds the statement HTML, `/api/preview-report` renders it, the client turns it into a PDF with `html2pdf.js`, and `/api/send-email` / `/api/send-salesperson-email` send it with nodemailer using the SMTP config from the DB (falls back to Ethereal when none is set). Sent reminders are recorded in `Reminder`.
- Insurances and contracts: files are uploaded to Vercel Blob through `/api/upload` (a public route). `*/extract` routes pull out the dates and parties and `*/bot` routes answer questions about the stored documents, through `generateText` in `src/lib/ai.ts`: OpenRouter (`OPENROUTER_API_KEY`, model `OPENROUTER_MODEL`, default `anthropic/claude-sonnet-5.5`, PDFs sent as `file` parts) or, without that key, Gemini (`GEMINI_API_KEY`, `gemini-flash-latest`).
- Cashflow merges open invoices and purchase invoices (by `cashflowDate`/`confirmedPaymentDate`/`dueDate`), active `RecurringPayment`s (`frequency` weekly/monthly/quarterly/semiannual/annual, chosen when adding one: weekly every 7 days from the start date, the others on `dayOfMonth` every 1/3/6/12 months from the start month, from today up to 12 months ahead; the list comes from BC `Recurring_Purchase_Lines_Excel`, plus manual ones created in the app with code `APP-<timestamp>`, which the sync leaves alone and which are deleted instead of deactivated), `CashflowManualEntry` rows, and per-company/currency starting balances (`CashflowConfig`). The default account/consolidated currency is CHF for CRAZE Group AG and EUR elsewhere. "Min. Saldo Consolidado" (next to the consolidated balance) is stored per company in ApiConfig `cashflow:minBalance:<company>` (`{amount, currency}`, via `/api/cashflow/min-balance`); a banner warns when the consolidated balance is below it or the projected balance of the open account first drops below it (converted with the day's rates), and those rows are flagged "Bajo mínimo".
- BANCO with the Amazon Vendor bank account (AMAVEN, or a bank named "Amazon Vendor"): the cash receipt is posted with the SPARKASSE statement against AMAVEN as usual; here AMAVEN gets each Amazon payment's breakdown so that every payment nets to 0 in AMAVEN. `POST /api/banco/amazon {bankNo, journalCode, from?}` reads the payments from the Finance Remittance API 2026-03-17 (`src/lib/amazonVendor.ts`, path `/finances/remittances/2026-03-17/remittances[/{uniquePaymentId}]`, `marketplaceId` required, 0.5 rps; the PDF's `/finances/remittance/v2026-03-17/headers` path is wrong and SP-API answers 403 to unknown paths; each `SP_API_VENDOR_REFRESH_TOKEN_<marketplace>` only returns its marketplace's payments (DE also PL/CZ), so all are read and deduplicated by uniquePaymentId; CRAZE GmbH reads every marketplace except UK, Craze UK (CRAZE Toys Ltd) only Amazon UK (GBP), other companies have no Amazon (`amazonCompany`); only payments in the bank's currency). Payments are stored in ApiConfig `reporting:setting:amazon:remittances:<company>:<bank>` (`done`, item details of the missing ones, `checkedUntil`); each read asks Amazon only from a week before the last check (60 days the first time, or the optional "Releer desde" date, or the oldest payment still IN_PROGRESS), and payments already done more than a week ago are not checked again. Done = AMAVEN has non-bank entries (customers/vendors/accounts) with Document No. = payment number, or the payment is in the batch. For a missing payment, one line per remittance item: the open customer/vendor invoice or credit memo with that number (applied), else the customer/vendor most used for that country's payments in AMAVEN. IN_PROGRESS payments are listed apart and not suggested.
- Payment-method codes such as `MARKANT` (factoring) change how invoices are handled in cashflow and dunning. Check recent commits before touching that logic.

**Dashboard (`/`, `GET /api/dashboard`).** Built from the synced Postgres data, except the "Pagos Internacionales (China)" cards, which come live from BC through `payablesReport` (same as Reporting: open vendor entries whose own payment method is CHINA TRF, remaining amount in LCY, confirmed = Scheduled Payment Date set; cached 1 h, stale-while-revalidate), falling back to the synced data if BC fails. With `ALL` it shows CRAZE Consolidated: every company in `GROUP_COMPANIES` computed the same way, converted to EUR with `eurRate` (`Currencies_Excel` of CRAZE GmbH; invoices by their currency code, otherwise the company's currency), without intercompany customers/vendors (INTERGROUP or named "CRAZE …"); cash available is summed per currency.

**Reporting (`/reporting`).** Monthly management report (KPIs / Operacional / Dirección tabs; KPIs repeats the main indicators of other reports from their caches, each with a small link to its source report, e.g. the 4 inventory KPIs → `/inventory-analysis?month=`; month selector, language from the app selector, no AI key points on the page, PDF via the browser print dialog with the print CSS in `globals.css`). `ReportPage` (`src/app/reporting/ReportPage.tsx`) also serves the menu item Análisis Inventario (`/inventory-analysis`: inventory value by Location Code and CHINA TRF purchases, plus `GET /api/reporting/inventory-analysis?month=` from `inventoryAnalysis.ts`: the inventory at every month end of the report year and the whole previous year, as compact rows [date, item, location, value, qty] with item attributes from the CRAZE GmbH custom `items` (range, categorizationCode, line, license, businessUnit, rawArticle, itemToRoot) and the Royalties Royalty Code, cached 6 h as one entry; the page groups by the chosen characteristic, compares with the same month end of last year and filters the monthly line chart by the clicked rows). Its KPIs (`?kind=kpis`, `inventoryKpis.ts`, cached and refreshed daily) are destroyed value (Negative Adjmt. value entries in DESTR-M+F), pallets (stock per item ÷ PAL unit qty from `Item_Units_of_Measure_Excel`, rounded up per item) and Average Days in Stock (FIFO over Item_Ledger_Entries_Excel of Inventory items, transfers excluded, by exit month); CHINA TRF purchases use `?kind=purchases` (posted purchInvLines). Month selectors across the app show months as MM/YY (`fmt.monthCode`). These analysis caches keep closed months a week (`refreshAfter`) and the current/last month a day; `.github/workflows/warm-inventory.yml` precomputes them nightly (CRAZE: last 12 months; other companies: current and last month). `.github/workflows/warm-daily.yml` (05:15 UTC, before the working day) precomputes what every other page opens by default, with the same default dates as the pages: Dashboard (each company + ALL), Reporting sections of the previous month per company, Controlling (Compras, Consumed Provisions, Intercompany per company, Ventas por licencia, Order Date, BWA Power BI), BWA Analytics, Royalties (last quarter, group, MG) and Commercial facts (each company, this and last year); routes it warms have `maxDuration` 300. When you add a cached report or change a page's default dates, add/update its call there. Caches whose period ends today (Compras, Intercompany) are keyed "hasta hoy" so they survive the date change. PM Classification comes from `Item_Card_Excel`, read in parallel by first character of the item no. (the whole page takes over a minute). It replicates a report built from BC exports and two Power BI files, but reads BC live:
- One route per block, `/api/reporting/<section>?month=YYYY-MM[&force=1]`, backed by `src/lib/reporting/*`. Heavy BC reads are cached in `ApiConfig` (`reporting:cache:*`, see `cache.ts`); `REPORTING_NO_CACHE=1` bypasses the DB for scripts. `cached()` is stale-while-revalidate (used by Reporting, Controlling and Royalties): it always returns the last stored data at once and, when it is older than 1 h (or its shorter max age), recomputes it in the background with `after()` (lock key `reporting:refreshing:*` so only one refresh runs). It only waits for BC when nothing is stored or with `force=1` (the refresh button). Caches longer than a day (AI key points by content hash) aren't refreshed hourly.
- Inventory (`inventory.ts`): OData `ValueEntries` (a BC Query: no `$orderby`/`$apply`, fetched in parallel by `Entry_No` ranges), excluding entries without `Item_No`; matches page 80016 "Inventory Value CRZ". Value per location = location qty × item unit cost. The 2023 depreciation % per item is a fixed list (setting `depreciation2023`).
- Receivables/payables (`ledgers.ts`): custom API `custLedgerEntries` / `vendorLedgerEntries`. "Open at month end" = posted ≤ date and (open, or closed after the date); BC rejects `or` across fields, so it runs two queries. INTERGROUP is excluded from customer receivables; CHINA TRF confirmed = `scheduledPaymentDateBCT`.
- Provisions (`provisions.ts`): `General_Ledger_Entries_Excel`, every entry with `Document_No` starting with `PROV` (PROV-00049… and also PROV1, PROV3… royalty reinvoicing) posted in the report year up to the cutoff. Each month a new PROV document re-estimates a provision against a balance-sheet account (3071 13 Konditionen, 3071 12 Lizenzen, 3071 08 KAM, 3072 01 Marketing, 3072 02 Amazon Promotions). A document's series is the provision account (30xx) of its first entry on one; PROV documents without a 30xx account (PROV1, PROV3: royalty reinvoicing against 3401 01 / 1260 01) are not provisions made and are left out here (they count as consumed royalties in Controlling). The open amount of a series is that account's balance over all its PROV entries, shown on the series' latest document. That row's original is the year's provisions in the series: what its documents post to income-statement accounts (classes 4–7: 4769 02, 6020 10, 6600 30, 6600 31, 6837 00), matching the P&L balances and consumed = original − open. Series 3072 02 is its own type, Amazon Promotion. Amounts are shown with the expense sign (e.g. PROV-00049 CRAZE 09/2026: open 472.987,87 = 3071 13). `/api/reporting/provision-check?doc=&month=&company=` shows the live calculation for one document.
- BWA (`bwa.ts`): custom `glEntriesUnion` + `mappingAccounts` + `bwas` (Formula lines sum other codes), GBP/CHF converted with `Currencies_Excel`, sign inverted. A company column includes its elimination entries; Intercompany = elimination entries; Consolidated = everything else.
- Cashflow (`cashflowReport.ts`) reuses `src/lib/cashflow.ts`, overdraft limit setting `overdraftLimit` (default −1 M€), 4-month horizon. Key points are generated by AI (`summary.ts`) from the figures the page already loaded: OpenRouter via `src/lib/ai.ts` when `OPENROUTER_API_KEY` is set, else Claude (`@anthropic-ai/sdk`, `claude-opus-5-5`) with `ANTHROPIC_API_KEY`, else Gemini.

**Royalties (`/royalties`).** `GET /api/royalties?from=&to=[&force=1]` → `src/lib/royalties.ts`, cached like reporting. It reads BC page/table 60000 "AIT Documents LM Components" through its OData web service. The service is found by name (`/lm_?components?|royalt/i`) unless setting `royaltiesService` sets it, and field names are matched against candidate lists. The User Setup record for the app user ACOUNTING must exist in each company or BC refuses the page. If BC fails, the page shows the error; there is no Excel fallback. Lines with Main Item are dropped, and so are intercompany lines (`isIntercompany`: INTERGROUP customer, customer named "CRAZE …", customer dimension "Craze Intercompany", or VAT group INTERCOMPANY…). The LM Royalty Code is ignored. The code always comes from the item card (table 27) in company `CRAZE` (GmbH): the custom API `items`, or an OData page whose name starts with Item and has a `royalt*` field (setting `royaltiesItemService`), cached 6 h. An item with no card there takes its base item's code (letters stripped off the end, e.g. 48412MEILI → 48412), or else keeps its LM code. The LM provision is ignored too. Provision = turnover × % Domestic Royalty (% FOB Royalty when the shipment method is FOB, unless the code's % FOB is 0) from page 80007 "Royalties" in `CRAZE`, OData service `RoyaltiesCRZ` (setting `royaltiesRatesService`), cached 6 h. Contract dates are not applied, the same as in BC's LM. The code field is `License_No`. If RoyaltiesCRZ can't be read, the report keeps the LM's own provision (`Total_Provision_Royalties`) and shows a warning. UK amounts are in GBP and Group AG amounts in CHF (`companyCurrency`). The page has its own CRAZE Company selector (one or several companies, or CRAZE Consolidated = all of `GROUP_COMPANIES`; one `/api/royalties?company=` call each, rows tagged with the company; several companies are always shown in EUR) and a TOTAL row under the Royalty Code summary. A single company can be shown in EUR using the `Currencies_Excel` rate of CRAZE (the same one the BWA uses). The rate is editable and the conversion is done client-side. A code missing from that table has no provision and is listed on the page. Licences a company may not sell are left out (`EXCLUDED_CODES`: BLUEY in UK). The rest is grouped by Royalty Code × bill-to country × item. Price = turnover ÷ qty and rate = provision ÷ turnover. The default period is the last calendar quarter; a year + Q1–Q4 selector next to the presets picks any quarter. In CRAZE the page also shows a group summary (`GET /api/royalties/group`, `groupRoyaltiesReport`). It has one row per licence and one column per company in `GROUP_COMPANIES`, each from BC, converted to EUR on the page with the editable `Currencies_Excel` rates. Below it is the Minimum Guarantee summary (`GET /api/royalties/mg?to=`). The contracts and instalments live in `src/lib/royaltyContracts.ts`, and several Royalty Codes can feed one licence (Toys + Cosmetic). For each guarantee, the group's provision from the contract start up to `to` is assigned by billing country (Viacom: GSA vs UK/Channel Islands; Bluey: everything except UK). Each contract has an `owner` company and contracts are sorted by owner in `GROUP_COMPANIES` order. The MG route returns the provision by code, country and date (`buildReport(..., trackDates)`). Each instalment active at `to` opens a period that runs until the next instalment or `to`; the first period starts at the contract start. That period's Provision Royalty goes to MG while active MG remains, including MG left over from earlier instalments, and the rest is Royalty to Invoice. To MG + To Invoice = Provision on every row. Future instalments are shown but not consumed.

**Controlling (`/controlling`).** Several controlling reports switched with header tabs, like Reporting. Each report (except Consumed Provisions, which uses the menu company) has its own CRAZE Company selector (`CompanySelect.tsx`, starts from the menu company, passes `?company=` to the API) with a "CRAZE Consolidated" option that loads every company and merges them in the browser: Order Intake and Ventas por licencia in EUR (`eurRate` from CRAZE `Currencies_Excel`), Compras por artículo/proveedor merged by item with each vendor tagged with its company (`purchaseData.ts`); BWA año a año is per company only. Any view that drills down to purchase invoices offers an "Agrupar por" selector (month, vendor, Source Code/account, none) and sortable columns.
- Compras por artículo: `GET /api/controlling/purchase-items?from=&to=` → `src/lib/controlling/purchaseItems.ts` (cached 1–6 h; a period ending today or later is cached as "hasta hoy" so the same entry serves every day, refreshed hourly in the background; `maxDuration` 300 because a cold year takes 40–60 s; the current year of CRAZE is precomputed nightly by `warm-inventory.yml`). Posted purchase invoice lines (custom API `purchInvLines`, type Item) + headers (`Posted_Purchase_Invoice_Excel`), credit memos from an OData service for page 140 with its lines (found by name `/purch.*cr.?memo/i`, not the `CS_` Document Capture ones) or, while it isn't published, from G/L Entries (purchase entries of each credit memo grouped by Gen. Prod. Posting Group → the item with that group, no quantity/unit cost; header dates from `CS_PostedPurchaseCrMemos`), item card (v2 `items`; the `Item_Card_Excel` page takes >30 s), vendor card (`Vendor_Card_Excel`, including the Customer Group assigned to the vendor, `Customer_Group_Code_BCT`, with its description from table 80008 via custom API `customerGroups`; shown before Country/Region in both purchase views), General Posting Setup (`General_Posting_Setup_Excel`, current Purch./Cr. Memo account per bus. × prod. group) and the historical G/L account from `General_Ledger_Entries_Excel` (Gen. Posting Type Purchase, same document and Gen. Prod. Posting Group as the line). Items of type Inventory are excluded. Item → vendor → documents; item/vendor pairs with as many credit memos as invoices, or whose net is 0, are dropped.
- Compras por proveedor (`PurchaseVendorsView.tsx`): the same `/api/controlling/purchase-items` data regrouped vendor → item → documents (grouping by month, G/L account or invoice/credit memo), to check each vendor invoices the right items.
- BWA año a año: two uploaded P&L Excel files (`src/lib/controlling/plParse.ts`, parsed in the browser: DATEV BWA or the group BWA export, sign normalised to income +/costs −), stored per company in `ApiConfig` `controlling:pl:<company>:<A|B>` via `/api/controlling/pl`. Rows are paired by label or a DATEV↔group synonym list (editable per row, kept in localStorage); % on a selectable reference row; selected months only; top cost increases/decreases.
- Consumed Provisions: `GET /api/controlling/consumed-provisions?from=&to=` → `src/lib/controlling/consumedProvisions.ts`. Provisioned = PROV* entries in the period on the income-statement provision accounts (4769 02 Conditions, 6020 10 KAM, 6600 30 Marketing, 6600 31 Amazon Promotion, 6837 00 Royalties), i.e. the P&L balances. Shown next to it for reference, the LM calculation (page 60000 without Main Item lines): Conditions = `Total_Provision_Sales`, KAM = "Provision HHRR" (`Total_Provision_Bonus`), Royalties = `Total_Provision_Royalties`, Marketing = `Provision_Marketing` without Amazon customers, Amazon Promotion = `Provision_Marketing` on Amazon lines. Consumed = everything a purchase invoice/credit memo has on PROV-KONDITIONS / PROV-KAM / PROV-MARKETING / PROV-ROYALTIES / PROV-AMZPROM in the period, following the Document No. (purchase posting, PUR-DEFER releases and journal reclassifications posted with the same document number); PROV + number documents (PROV1, PROV3: royalty reinvoicing), journal documents on those accounts with no purchase document behind them (Skonto Reclassification…) and, in PROV-… documents, whatever reduces the concept's provision account (3071 13, 3072 01, 3072 02, 3071 12) against other balance accounts (= series account + P&L + PROV-* account, e.g. PROV-00049's transfer from 3071 06) also count, so consumed matches the Reporting (provisioned − open). The page also shows the LM calculation by `Customer_Group_Code` (name from the custom API `customerGroups`) next to what that group consumed: purchase invoices/credit memos whose vendor is one of the group's LM customers, matched by VAT number, then exact normalised name, then first word when it fits only one group, then the Customer Group name (all its words except the country must be in the vendor name; a matching country wins). Each position carries `final` (Abschließend festgesetzt (X) = definitiva, Nicht abschließend (X) = no definitiva; DHL: "Kz. Erledigung (Position): 5 - Abschließende …"), shown on the position and counted per AT/C in the summary, and `findings` = the Bescheid's "Positionsbefund" (what the inspection saw), shown under the position and also used to assign items by description (e.g. "Sticky Hand"). Per AT/C, "Pedido / contenedor" sets the order / China invoice and container by hand (`POST /api/customs/history/manual {atc, orders, transport}`, stored in `customs:tariff-manual:<company>`, returned as `manual`); it overrides what the PDF says when that AT/C is analysed again (the page calls `recompute=<AT/C>`), a BC invoice number (CRZ-PI26-04421) is turned into its Vendor Invoice No., and with a China invoice the check runs even when the PDF has no positions (its items are listed without position). Items with figures inside carry two codes in BC's Tariff No. ("950590000/950300499": item / its figures); customs declares them as the item's position plus the next position "Figur(en) zu Position N" (0 %). `tariffStatus` (`figureTariffs` maps N → the figures' code): one BC code = compared with the position only (a figures position is not needed); two codes = the first against the position and the second against its figures position, and "Distinto" with a note when that figures position is missing or differs. A display (FSDU whose contents are in its BOM, listed broken down) that comes out "Distinto" in a position declared at 0 % is accepted automatically (`acceptDisplay`: Coincide + note "the difference is the packaging"): customs declares the contents separately and the display only as packaging. Each call processes the new AT/Cs that fit in ~40 s and returns `pending`; `HistoryView.tsx` keeps calling until it is 0. One table whose rows are grouped by declared tariff code or by AT/C ("Por código arancelario" / "Por AT/C", same columns, remembered in localStorage): by code (positions, Zollwert, Zoll, items with their BC Tariff No., status and other codes the same item was declared under) or by declaration (codes, positions, Zollwert, Zoll, items, status), which expands to its Zoll invoice/order/China invoice and the `TariffTable` (shared with `TariffCheck.tsx`); Excel export.

**OCR (`/ocr`).** Supplier invoices in PDF → unposted Purchase Invoice in BC, like the Aduanas importer but for any vendor, **without AI** (rules only, `src/lib/ocr.ts`). `POST /api/ocr/parse` (multipart `file`, one PDF per call because of Vercel's 4.5 MB body limit, optional `vendor` to redo it for a vendor picked by hand), `POST /api/ocr/create` (multipart `data` + `pdf`), `POST /api/ocr/attach` (one extra file per call), `GET /api/ocr/vendors?q=`. Text with `unpdf`; a PDF without text (screenshots such as the Uber receipts, scans) is read in the browser with Tesseract (`src/app/ocr/tesseract.ts`, `tesseract.js`: pages rendered with unpdf at ~2000 px, deu+eng+spa, no AI and no cost) and sent again as `text`; then, with no labelled date, the last date in the text is the invoice date (Uber: the payment line). The PDF's currency (`detectCurrency`: EUR/USD/GBP/CHF/CNY by code or symbol, any other ISO code only next to an amount, e.g. "71,00 MOP") picks the model among the vendor's invoices in that currency when there are any (Uber Belege 7300610: AED/CHF with 19% SERVICES, EUR with OHNE MWST) and is always the proposed invoice currency, even with no previous invoice of the vendor in it (warning, and another if the code is not in v2 `currencies`) (editable; the company's local currency goes empty, PATCHed on the v2 header before the lines). Uber rule (`uberRules`, vendor name /uber/): the payment date and time ("Zahlungen … 20.10.26 18:29") is the invoice, posting and due date and the Vendor Invoice No. ("20.10.26 18:29"), every line OHNE MWST. Amounts follow the VAT % of the proposed lines' VAT Prod. Posting Groups (`VAT_Posting_Setup_Excel` with the vendor's VAT Bus. Posting Group from `Vendor_Card_Excel`, or the proposed one; Normal VAT = its %, Reverse Charge = 0, cached 6 h): when every line has the same %, net/VAT/total are searched again with only that % (0 % = the PDF total is the net) and the lines rescaled; the result returns `vatRates` so that changing the Grupo IVA of a single-line invoice on the page recalculates its amount as total ÷ (1 + %). The line's Grupo IVA is a select of the company's VAT Product Posting Groups (`GET /api/ocr/vat-groups`, v2 `taxGroups`, cached 6 h). With no invoice no. in the PDF, a model number made of its date ("UBER_30/10/26", "28092026/6") is rebuilt with the new date, without the day counter. Vendor = best score over the company's v2 `vendors` (cached 6 h with each vendor's invoice count of the last year, plus our own VAT from `companyInformation`, which is ignored): identifiers in the PDF (VAT, IBAN, mail/web domain) learnt from invoices created here (setting `ocr:hints:<company>`; an identifier seen with two vendors is dropped), the card's VAT/e-mail/website, the words of its name (more matching words and the full name win), the currency (document vs vendor, `(USD)` in the name) and how often it invoices; vendors named CRAZE… only by identifier. History = the vendor's 15 most recent posted invoices (v2 `purchaseInvoices`, newest by document number, since the way they are entered keeps improving) with their Posted Purchase Invoice Lines (custom `purchInvLines`; `vatProdPostingGroup` = v2 `taxCode`, v2 lines only give the VAT identifier) and Posting Description (= custom `vendorLedgerEntries.description`; posted headers don't publish it), plus the attached PDF text of up to 5 with different lines. `propose()`: the model is the history invoice whose PDF is most similar to the new one (word Jaccard; ties → newest; no PDFs → newest). Before that, a history invoice whose single item number (≥ 5 digits) appears in the new PDF is the model (Amazon EU SARL debit notes: one item per Amazon agreement, item no. = the `MDF#` number, e.g. "MDF# 99009045: … Accrual (Damage Allowance External)" → item 99009045). When the model's item was written in its own PDF, the new PDF's value at the same spot replaces it if it is an item in BC (v2 `items`, with its description); otherwise the document is not an agreement (Born To Run, promotions, chargebacks also carry an MDF# that is not an item) and it is proposed again without such agreement invoices as model, with a note in the comment to create the item if it is a new agreement. Fixed Amazon rules after the model (`amazonRules`, vendor name /amazon/i): a PDF mentioning Rebate or Flexible → AA-00069 FLEXIBLE ASIN BASED, 19% DEBIT NOTE (other promotions follow the model); Amazon Ads lines (AA-00015, reverse charge) → 19% SERVICES and header VAT Bus. Posting Group `UE` (editable on the page, PATCHed through OData `purchaseDocuments` before our lines are added). Its lines are copied; amounts are only the totals: taxable base × rate = VAT and base + VAT (+ a tax-exempt part, e.g. Meyer's Sohn GmbH "MwSt frei 45.00") = total, all found in the text (the model's rate first, then common rates), or for tax-free vendors the most repeated large amount. The model's lines are split into taxed/untaxed by the subset whose amount × rate = its VAT; the base goes to the taxed lines and the exempt part to the others (e.g. KZ. 66.2 vs OHNE MWST), each in the model's proportion; otherwise the net is spread like the model. Invoice no., invoice date and due date are read in the new PDF at the same label where the model's values were in its PDF (generic labels as fallback; due date empty = BC computes it); posting date = the date at the model's posting-date spot when it differs from its invoice date (Meyer's Sohn GmbH: ETS/ATS; ETS = ATS, ETD = ATD, ETA = ATA), else the invoice date. References in Description/Description 2/Posting Description that came from the model's PDF (e.g. Meyers "MRM-328-2376 / CN2667696") are replaced by the value at the same label, or by the only token with exactly the same shape; BC's default Posting Description ("Invoice 10044") is not copied. Every field and line is editable on the page; it warns about a vendor that is not clear, currency ≠ vendor currency, credit notes (not created here), lines ≠ PDF net, references not found, and an existing Vendor Invoice No. for that vendor (`force` after confirming). Two import options, each with its own Procesar button (nothing is read until it is pressed): 1 = several PDFs, one invoice each; 2 = one row per invoice with its attachments (pick or drag onto the Factura / Adjuntos boxes or the row: the PDF whose name looks like an invoice is the invoice, the rest attachments; a new empty row appears when the last one gets its invoice). Attachments are not read; they are sent to their row's invoice after it is created. Both options also take Outlook e-mails (`.msg`, or `.eml`): `src/app/ocr/emailFiles.ts` extracts their PDF attachments in the browser (`@kenjiuno/msgreader`, `postal-mime`, loaded on demand); a drop with no files (some Outlook drags) shows a hint to save the file first. Create = v2 `purchaseInvoices` + PATCH due date, deletes BC's standard vendor lines, posts ours, Posting Description through OData `purchaseDocuments`, attaches the PDF (`src/lib/bcWrite.ts`, shared with Aduanas), logs the action and learns the identifiers.

**D-FORCE/MF (`/magazines`, menu label D-FORCE/MF, formerly MAGAZINES; only for Craze Entertainment; permission `dforce`; `/dforce` redirects here).** Header tabs D-FORCE (`DForceView.tsx`) and MAILFINISH (`MailfinishView.tsx`).

**MAGAZINES › D-FORCE.** It turns the monthly D-FORCE-ONE Gutschrift (PDF) and its Curasoft Excel export into lines for three BC documents. `POST /api/dforce/process` (multipart `pdf`, `excel`) → `src/lib/dforce.ts`. The PDF is read server-side with `unpdf` (rows rebuilt by y position) and the Excel with `xlsx`.
- The document comes from the Excel movement type, never from the PDF appendix. Lieferungen/Lieferdifferenzen (Vorgang 10/11/20/21) go to the Sales Invoice, Remissionen (160/161) to the Credit Memo, and everything else to the Purchase Invoice. Each Excel sales row gives exactly one line. The PDF only supplies the channel (Sparte) and the order, matched by title, issue, quantity and amount. Repeated PDF rows are dropped, and PDF-only or Excel-only rows are reported as warnings.
- Sales Invoice: one line per Lieferungen/Lieferdifferenzen row, with Description 2 = Sparte (channel).
- Sales Credit Memo: RI/RA with positive quantities. Bahnhofsbuchhandel and all RA lines get Return Reason `NON-REC`. BC generates their negative reversal lines itself, so the app doesn't output them. Project Task No.2 is `004.001` on returns without a reason code and empty on NON-REC lines.
- Purchase Invoice: vendor `VE-00111`, from Excel Vorgang 220/230/240/250 grouped by title and issue, mapped to service items AA-00005/06/10 with project tasks 002.00x. Rows without a magazine (TitelNr 0, e.g. Vorgang 250 "OHL Transport Galupy und Inkee Mailfinish" 2.173,10) become one line of their concept with no project or task, at the end, as in CEN-PI26-00030 / 00066.
- Item and project come from the TitelNr (`TITLES`: 4191 → 05995/35420, 4192 → 05993/38791, 4193 → 05994 …_SPECIAL) plus the issue suffix `_YYMM`.
- Item description and unit cost are read from BC standard API `items` of Craze Entertainment.
- Check: invoice − returns − purchase = the PDF's "Summe Netto".
- Return provisions (`src/lib/dforceProvisions.ts`, computed client-side so unit costs can be edited), all against 3071 00 as in August 2026:
  - Invoice: `PROV.<GAL|INKE|GALSP><MM>/<YY>` on 4300 00 = 80% of sales, and `INV.PROV.…` on 5881 00 = −(80% of units × unit cost), with a negative journal amount. Only issues delivered that month (LI/LA lines) are provisioned.
  - Credit memo: the returns release both entries at 100%: negative on 4300 00 and positive on 5881 00.
- Send to BC (`POST /api/dforce/create`, multipart `data` = {kind invoice|credit|purchase|journal, ref = Gutschrift no., date, lines, force} + `pdf` + `excel`; one call per document, `maxDuration` 300) → `src/lib/dforceBc.ts`. Documents are created unposted through v2 (`salesInvoices`/`salesCreditMemos`/`purchaseInvoices` + lines: item, qty, unit price/cost, Description 2, `taxCode` 7% GOODS/7% SERVICE, `locationId` of D-FORCE on sales), with External Document No. / Vendor Invoice No. = Gutschrift no. (used to detect duplicates, `force` after confirming); before the lines, "Ignore Custom Qty. Fields" (`AIT_Ignore_Custom_Qty_Fields`, not in v2) is switched on in the sales header through those same pages 43/44 (otherwise BC enforces the magazines' sales multiple, e.g. 30; setting `dforceSalesHeaderService`); BC's standard customer/vendor lines are deleted, a half-created document is deleted on error, and the PDF and the Excel are attached (`attachFile`). Project No., Project Task No., Project Task No.2 and Return Reason Code are not in v2 lines: they are PATCHed afterwards through an editable OData lines service via `@odata.editLink` (relative to the OData root, already with `Company('…')`), rows by Document No. + Line No. (= v2 `sequence`). Sales use the extension fields `AIT_Job_No` / `AIT_Job_Task_No` / `AIT_Job_Task_No_2` (that's where every posted D-FORCE sales line has its project; the standard Job No. stays empty) on the lines of pages 43/44 published as `Sales_Invoice_Excel` / `Sales_Credit_Memo_Excel` (entities `…SalesLines`); purchases use the standard `Job_No` / `Job_Task_No` (`purchaseDocumentLines`, `Purchase_Lines_Editable_Excel`…; the next service is tried when the first line can't be PATCHed). Setting `dforceLinesService` {invoice, credit, purchase} overrides the service; if none works the document stays and a warning says what to fill in BC. Provisions go to General Journal Batch `D-FORCE` (v2 `journals` + `journalLines`, G/L Account against 3071 00), the files attached to the first line; lines already in the batch with the same Document No. and date count as duplicates. The posting date (period end of the Gutschrift) is set at the top of the page.
- The page also exports the "Output Format" config-package layout: sheets `Sales Line` (37) and `39 Purchase Line` with the document numbers created in BC, plus a `Provisiones 3071 00` journal sheet.

**Magazine Profitability (`/magazine-profitability`, own menu entry, only for Craze Entertainment; permission `magazine_profitability`; view `MagazineProfitabilityView.tsx`).** Profit per magazine issue. `GET /api/magazines/analysis[?force=1]` → `src/lib/magazineAnalysis.ts` (cached 1 h, stale-while-revalidate, warmed by `warm-daily.yml`). The app corrects wrong/missing projects (`corrections`, listed in a blue "corregidas en la app" block and noted on each line, `fixed`): D-FORCE sales lines whose project belongs to another magazine count under their item (in every case the line description names the item's magazine, so the project is the wrong field); Magazine Ads (description /magazine ads/) go to the magazine named in the document's External Document No. (v2 `salesInvoices`/`salesCreditMemos`, "MAGAZINE - INKEE 01/25 ADS", "… 01/26 SPECIAL ADS" → 05994), overriding the project, with task 001.004 when missing; Ads with neither (External Document No. IN-CE-0000x) go to the magazine of the same title whose On Sale Date is closest to the posting date (≤ 21 days, preferring issues without Ads yet: Ads are invoiced on the on-sale day). Purchase lines without project (vendors that have project lines elsewhere) get the magazine from the document's attached PDF (v2 `documentAttachments`, text via `pdfText` from ocr.ts, `magazinesInText`: "INKEE“, Ausgabe 0225" → 05993_2502, SEVEROTISK "Galupy 3/26" / "Galupy 3/2026" → 05995_2603, "GALUPY SPECIAL" → 05994) when it names exactly one known magazine, with the task that item usually has on project lines (AA-00041 → 004.004); invoice/credit memo pairs without project that cancel out (same vendor, item, opposite amount: re-posted later with project) are dropped before, so the PDF never double-counts a cost; each document's PDF is read once and stored in setting `magazines:pdf-mags` (BC errors are not stored). Lines still without magazine are listed as "sin revista" with the PDF finding; they can be validated ("no es de ninguna revista", `POST /api/magazines/analysis/validate {lines:[{key,doc,description}], validated}`, key = kind|document|line no., stored in setting `magazines:validated`, returned by the GET outside the cache, logged) so they are no longer flagged; or assigned by hand to a magazine + task from the row's selectors (`POST /api/magazines/analysis/assign {key, magazine, task} | {key, remove}`, setting `magazines:manual`, applied by `applyManual` when the GET serves the cached data, listed among the corrections with "Quitar"; the suggested task is the item's usual one). The blue corrections block has an OK button: the seen corrections are kept per browser (localStorage `crz-magprof-fixes-ok`) and the block moves to the bottom of the page until new ones appear; storage and handling (AA-00009 / AA-00010) without project are general costs and not listed; invoice + credit memo pairs that cancel out are dropped. Return provision (Forecasted Returns, task 001.002, computed in the page by `withProvision`): % of sales expected back, general (input "Provisión devoluciones %" in the header) or per magazine, plus close/reopen per magazine (`POST /api/magazines/analysis/provision {defaultPct} | {item, pct?, closed?}`, setting `magazines:provisions`, returned by the GET outside the cache, logged).
